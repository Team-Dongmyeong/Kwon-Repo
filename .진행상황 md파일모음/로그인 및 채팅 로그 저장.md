# 마음잇기 — Supabase 연동 보고서 (회원가입 · 로그인 · 채팅 기록 DB 저장)

> 최종 갱신: 2026-09-28
> 이 문서는 배포 환경(Vercel + Render)에서 GPT 채팅 연동을 끝낸 뒤, **Supabase DB를 붙여 회원가입·로그인·채팅 기록 저장이 실제로 동작하도록 만든 과정**을 순서대로 정리한 것. 기존 배포 가이드(`배포 과정 정리 보고서`)의 다음 단계에 해당함.

---

## 0. 전체 그림

```
[브라우저 / Vercel 프론트]
   Signup.jsx · Login.jsx · Chat.jsx
   AuthContext.jsx (로그인 상태 + 토큰 보관)
   chatApi.js (백엔드 호출)
          │  모든 요청에 "Authorization: Bearer <로그인 토큰>" 첨부
          ▼
[Render 백엔드 / FastAPI main.py]
   /auth/register · /auth/login · /auth/refresh · /me
   /chat · /chat/sessions · DELETE /chat/sessions/{id}
          │  토큰으로 사용자 확인 → user_id 기준으로 읽기/쓰기
          ▼
[Supabase]
   auth.users (계정 + 암호화된 비밀번호)
     └─ 트리거 → profiles (이름, 이메일, 감정 점수 …)
                   └─ chat_sessions (대화방)
                        └─ chat_messages (말풍선)
          │
          ▼
[OpenAI GPT-4o mini]
```

핵심 원칙
- 브라우저는 **Supabase에 직접 접근하지 않고**, 반드시 백엔드를 거친다.
- 백엔드는 로그인 토큰으로 "누가 보낸 요청인지" 확인한 뒤, **그 사람(user_id)의 데이터만** 읽고 쓴다.

## 1. 출발 상태 (로컬에서만 되던 것)

로컬 개발 단계에서 이미 준비되어 있던 것:

| 항목 | 내용 |
|---|---|
| SQL (`user_info_query`) | `profiles` 테이블 + 회원가입 시 자동으로 profiles에 행을 넣는 트리거 |
| `backend/DB/config.py` | `.env`의 `SUPABASE_URL`, `SUPABASE_KEY`로 Supabase 클라이언트 생성 |
| `backend/DB/supabase_client.py` | `register_user`, `login_user`, `get_user_info_query`, `update_emotion_scores` 함수 |
| `requirements.txt` | `supabase` 등 패키지 목록 |
| `.env` | 실제 키 값 (`.gitignore` 처리) |

### 1-1. profiles 테이블과 트리거 (`user_info_query`)

```sql
CREATE TABLE public.profiles (
    id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
    name VARCHAR(50) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL,
    overall_sentiment_score FLOAT DEFAULT 0.0,
    score_fear FLOAT DEFAULT 0.0,
    score_surprise FLOAT DEFAULT 0.0,
    score_anger FLOAT DEFAULT 0.0,
    score_sadness FLOAT DEFAULT 0.0,
    score_neutral FLOAT DEFAULT 0.0,
    score_happiness FLOAT DEFAULT 0.0,
    score_disgust FLOAT DEFAULT 0.0,
    recommended_jobs TEXT[],
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

CREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS TRIGGER AS $$
BEGIN
  INSERT INTO public.profiles (id, email, name)
  VALUES (NEW.id, NEW.email, COALESCE(NEW.raw_user_meta_data->>'name', '사용자'));
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE OR REPLACE TRIGGER on_auth_user_created
  AFTER INSERT ON auth.users
  FOR EACH ROW EXECUTE FUNCTION public.handle_new_user();
```

→ **이 쿼리는 이미 실행된 상태이므로 수정·재실행하지 않는다.** (재실행하면 "profiles already exists" 에러)

### 1-2. 회원가입 정보는 어디에 저장되나

| 입력 항목 | 저장 위치 | 비고 |
|---|---|---|
| 이름 | `profiles.name` | 가입 시 `options.data.name` → 트리거가 복사 |
| 이메일 | `auth.users.email`, `profiles.email` | |
| 비밀번호 | `auth.users` (**해시로 암호화**) | 원문은 누구도 볼 수 없음 — 보안상 정상 |
| 비밀번호 확인 | 저장 안 함 | 두 입력값이 같은지 비교하는 용도로만 사용 |

Table Editor → `profiles`에서 이름·이메일 확인, Authentication → Users에서 계정 확인.

## 2. 배포 환경에서 Supabase가 동작하도록 한 설정

### 2-1. 폴더 구조

Render의 Root Directory가 `backend`이므로, DB 관련 파일은 전부 `backend/` 안에 있어야 한다.

```
backend/
├── main.py
├── prompts.py
├── requirements.txt      ← supabase 포함 (Render는 이 파일만 읽음)
├── .env                  ← 로컬 전용 (git에 안 올라감)
└── DB/
    ├── __init__.py       ← 빈 파일
    ├── config.py
    └── supabase_client.py
```

- **`__init__.py`**: "이 폴더는 import 가능한 패키지"라는 표시. Python 3.3+에선 없어도 대부분 동작하지만, 이름 충돌·도구 인식 문제를 막는 보험으로 빈 파일을 둔다.
- **대소문자 주의**: Windows는 `DB`와 `db`를 같게 보지만 Render(리눅스)는 다르게 본다. 폴더명과 `from DB...`가 정확히 일치해야 함.

### 2-2. config.py 확인 포인트

```python
import os
from dotenv import load_dotenv, find_dotenv
from supabase import create_client

load_dotenv(find_dotenv())
supabase = create_client(os.getenv("SUPABASE_URL"), os.getenv("SUPABASE_KEY"))
```

1. 키 값을 코드에 직접 쓰지 않고 `os.getenv()`로 읽을 것
2. 변수 이름이 Render에 등록한 Key 이름과 **글자 하나까지 동일**할 것
3. `load_dotenv("C:/...")`처럼 내 PC 경로를 쓰지 말 것 — Render엔 `.env`가 없어도 `load_dotenv()`는 에러 없이 넘어가고 대시보드 환경변수가 대신 쓰임

### 2-3. Render 환경변수

| Key | 값 | 용도 |
|---|---|---|
| `OPENAI_API_KEY` | OpenAI 키 | GPT 호출 (기존) |
| `SUPABASE_URL` | Supabase 프로젝트 URL | |
| `SUPABASE_KEY` | anon(public) 키 | 로그인·토큰 확인 |
| `SUPABASE_SERVICE_ROLE_KEY` | service_role 키 | 채팅 테이블 읽기/쓰기 (RLS 통과) |
| `ALLOWED_ORIGINS` | (선택) 추가 허용 프론트 주소 | CORS |

> ⚠️ `SUPABASE_SERVICE_ROLE_KEY`는 모든 데이터를 제한 없이 다룰 수 있는 키. **Render에만** 넣고 Vercel·GitHub에는 절대 올리지 않는다. 위치: Supabase → Project Settings → API Keys (탭이 나뉘어 있으면 "Legacy API Keys").

### 2-4. Supabase 대시보드 설정

| 위치 | 설정 | 이유 |
|---|---|---|
| Authentication → URL Configuration → **Site URL** | `localhost` → `https://kwon-repo-hwai.vercel.app` | 인증 메일 링크가 로컬로 가지 않게 |
| Authentication → Sign In / Providers → User Signups → **Confirm email** | 테스트 단계에선 **끄기** | 켜져 있으면 메일 인증 전 로그인 불가(`Email not confirmed`), 반복 테스트 시 메일 발송 한도(`email rate limit exceeded`)에 걸림 |

- Email Provider 세부 화면(Secure email change, Minimum password length 등)은 그대로 둬도 됨.
- Confirm email을 끄기 전에 만든 미인증 계정은 Authentication → Users에서 삭제 후 재가입.

## 3. 백엔드 API 추가 (main.py)

기존 main.py에는 `/chat`만 있었고, `supabase_client.py`의 함수를 **외부에서 호출할 엔드포인트가 없었음** → 프론트가 회원가입을 요청할 곳이 없는 상태였다.

### 3-1. 최종 엔드포인트 목록

| 메서드 | 경로 | 로그인 필요 | 역할 |
|---|---|---|---|
| POST | `/auth/register` | ✕ | 회원가입 (비밀번호 일치·길이 서버에서도 재검증) |
| POST | `/auth/login` | ✕ | 로그인 → `access_token` + `refresh_token` 반환 |
| POST | `/auth/refresh` | ✕ | 만료된 토큰 갱신 |
| GET | `/me` | ○ | 내 profiles 정보 (마이페이지용) |
| GET | `/chat/sessions` | ○ | 내 대화방 목록 + 메시지 |
| DELETE | `/chat/sessions/{id}` | ○ | 내 대화방 삭제 (남의 것은 불가) |
| POST | `/chat` | ○ | 메시지 전송 → GPT 응답 → DB 저장 |
| GET | `/` | ✕ | 헬스체크 |

### 3-2. 로그인 사용자 확인 방식

```python
def get_current_user_id(authorization: Optional[str] = Header(default=None)) -> str:
    # "Authorization: Bearer <access_token>" → supabase.auth.get_user(token) → user.id
```

로그인이 필요한 엔드포인트는 `Depends(get_current_user_id)`로 이 함수를 거치며, 토큰이 없거나 만료되면 401을 반환한다.

### 3-3. Supabase 클라이언트를 용도별로 분리

| 클라이언트 | 키 | 용도 |
|---|---|---|
| `supabase` (DB/config.py) | anon | 토큰 확인(`get_user`), 회원가입 |
| `db` | service_role | profiles·채팅 테이블 읽기/쓰기 |
| `_new_auth_client()` | anon, 요청마다 새로 생성 | 로그인·토큰 갱신 |

전역 클라이언트 하나로 `sign_in_with_password`를 하면 그 클라이언트의 로그인 상태가 **마지막 로그인한 사용자로 덮어써져** 여러 사용자가 섞일 수 있다. 그래서 로그인·갱신은 요청마다 일회용 클라이언트를 만들어 처리한다.

### 3-4. 토큰 만료 대응

Supabase의 `access_token`은 **1시간 후 만료**된다. 그대로 두면 1시간 뒤 채팅이 갑자기 끊김.
→ 로그인 시 `refresh_token`도 함께 받아두고, 401이 나면 `/auth/refresh`로 새 토큰을 받아 자동 재시도하도록 구성 (프론트 `authFetch`, 5-2 참고).

## 4. CORS: Vercel 주소가 여러 개인 문제

### 4-1. 증상

- 대표 주소(`kwon-repo-hwai.vercel.app`)에선 채팅이 되는데, Deployments에서 들어간 주소에선 안 됨
- 콘솔: `blocked by CORS policy: Response to preflight request doesn't pass access control check`
- Render 로그: `OPTIONS /chat 400 Bad Request`

### 4-2. 원인

Vercel 배포 하나에는 주소가 3개 붙는다.

| 주소 | 의미 |
|---|---|
| `kwon-repo-hwai.vercel.app` | 대표(Production) 주소 — 항상 최신 배포 |
| `kwon-repo-hwai-git-main-45888.vercel.app` | main 브랜치 최신 배포 |
| `kwon-repo-hwai-gr5zbgsyu-45888.vercel.app` | 그 배포 하나의 고유 주소 — **배포마다 바뀜** |

CORS 허용 목록에 대표 주소만 있었기 때문에, 나머지 주소에서 보낸 사전 확인 요청(OPTIONS)이 거절됨.

### 4-3. 해결

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=allow_origins,
    allow_origin_regex=r"https://kwon-repo-hwai(-[a-z0-9-]+)?\.vercel\.app",
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

`kwon-repo-hwai`로 시작하고 `.vercel.app`으로 끝나는 주소만 허용 → 세 주소 + 앞으로 생길 배포 주소 모두 동작, 다른 사람의 사이트는 계속 차단.

### 4-4. 참고

콘솔의 노란 경고 `Tracking Prevention blocked access to storage for https://cdn.jsdelivr.net/...pretendard` 는 Edge 브라우저가 폰트 CDN 저장소 접근을 막았다는 알림으로, 기능과 무관하므로 무시.

## 5. 회원가입·로그인: "가짜 처리"를 실제 연동으로 교체

### 5-1. 문제 발견 과정

| 관찰 | 해석 |
|---|---|
| `/docs`에서 직접 가입 → DB에 저장됨 | 백엔드·Supabase는 정상 |
| 웹에서 가입 → DB에 저장 안 됨 | 요청이 백엔드까지 안 옴 |
| Render 로그에 `POST /auth/register`만 있고 `OPTIONS`가 없음 | 세 줄 모두 `/docs`(같은 주소)에서 보낸 요청. 웹 프론트에서 온 요청은 **0건** |
| 아무 이메일·비밀번호로나 로그인됨 | 로그인도 서버 확인 없이 통과 |

`Signup.jsx`, `Login.jsx` 안에 다음 주석이 있었다:

```js
// TODO: FastAPI 회원가입 API 연동 전 임시 처리 — 입력 형식만 검증되면 가입 성공으로 간주
login({ email: form.email, name: form.name })
navigate('/home', { replace: true })
```

→ 서버에 아무것도 보내지 않고 화면만 넘기는 **모의(mock) 처리** 상태였음.

### 5-2. 수정 내용

**Signup.jsx**
- `VITE_API_URL + "/auth/register"`로 `name`, `email`, `password`, `password_confirm` 전송 (main.py의 모델 필드명과 일치시킴)
- 가입 성공 시 바로 `/auth/login` 호출 → 자동 로그인 후 `/home` 이동
- 이메일 인증이 켜져 있어 로그인 실패 시 "이메일 인증 후 로그인" 안내 후 `/login`으로
- 서버 에러(이미 가입된 이메일, 요청 한도 등)를 한국어로 표시

**Login.jsx**
- `/auth/login` 호출, **서버가 성공을 반환할 때만** 로그인 처리
- 틀린 계정 → "이메일 또는 비밀번호가 올바르지 않아요"
- 로그인 화면의 8자 길이 검사 제거 (길이 규칙은 회원가입에서만. `/docs`로 만든 6~7자 비밀번호 계정이 요청조차 못 보내던 문제 해결)

**AuthContext.jsx**
- 저장 정보: `{ id, email, name, accessToken, refreshToken }`
- id·토큰이 없는 예전 가짜 로그인 정보는 자동 폐기 → 재로그인 유도
- `authFetch(path, options)` 추가: 토큰을 헤더에 붙여 호출 → 401이면 refresh로 갱신 후 재시도 → 그것도 실패하면 로그아웃
- 로그아웃 시 예전 방식의 `maeum:chat-sessions` 삭제

## 6. 채팅 기록: 로컬 스토리지 → Supabase DB

### 6-1. 문제

F12 → Application → Local Storage에 두 항목이 있었다.

| 키 | 내용 |
|---|---|
| `maeum:auth-user` | 사용자 계정 (이름, 이메일) |
| `maeum:chat-sessions` | 챗 로그 (대화방 목록 + 메시지) |

`maeum:chat-sessions`의 **이름이 고정**되어 있어, 같은 브라우저에서는 누가 로그인하든 같은 기록을 읽었다 → **어느 계정으로 들어가도 같은 채팅 로그가 보이는 원인.**
또한 백엔드도 대화 맥락을 메모리(`session_store`)에만 보관해, Render 재시작·슬립 시 사라졌다.

### 6-2. 로컬 스토리지 구조 → DB 스키마 매핑

기존 챗 로그 구조 (Chat.jsx):

```
[ 대화방 { id, title, createdAt, messages: [ { role, text, time }, ... ] }, ... ]
```

| 로컬 스토리지 | Supabase |
|---|---|
| `maeum:auth-user` | `auth.users` + `profiles` (기존) |
| `maeum:chat-sessions` | `chat_sessions` + `chat_messages` (신규) |

| 테이블 | 컬럼 | 대응하는 기존 값 |
|---|---|---|
| **chat_sessions** | `id` (UUID) | 대화방 id |
| | `user_id` → profiles.id | (신규) 누구의 대화인지 |
| | `title` | title |
| | `created_at` | createdAt |
| **chat_messages** | `id` (자동 증가) | 메시지 순서 |
| | `session_id` → chat_sessions.id | 소속 대화방 |
| | `user_id` → profiles.id | 누구의 메시지인지 |
| | `role` (`user` / `assistant`) | role (`user` / `bot`) |
| | `content` | text |
| | `created_at` | time |

관계: `profiles (1) ─< chat_sessions (N) ─< chat_messages (N)`
- 계정 삭제 → 그 사람의 대화방 삭제 → 대화방의 메시지 삭제 (`ON DELETE CASCADE`)
- 추후 KcELECTRA 감정 분석 결과는 `chat_messages`에 컬럼을 추가해 메시지 단위로 저장 가능

### 6-3. SQL (`chat_table_query` — 새 쿼리로 생성)

SQL Editor → **+ New query** → 이름 `chat_table_query` → 아래 내용만 붙여넣고 Run.
(`user_info_query`에 이어 쓰지 않는다. 전체 재실행 시 profiles 중복 생성 에러)

```sql
CREATE TABLE IF NOT EXISTS public.chat_sessions (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID NOT NULL REFERENCES public.profiles(id) ON DELETE CASCADE,
    title TEXT NOT NULL DEFAULT '새 대화',
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

CREATE TABLE IF NOT EXISTS public.chat_messages (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    session_id UUID NOT NULL REFERENCES public.chat_sessions(id) ON DELETE CASCADE,
    user_id UUID NOT NULL REFERENCES public.profiles(id) ON DELETE CASCADE,
    role TEXT NOT NULL CHECK (role IN ('user', 'assistant')),
    content TEXT NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS idx_chat_sessions_user ON public.chat_sessions (user_id, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_chat_messages_session ON public.chat_messages (session_id, id);

-- 정책 없이 RLS만 켜면 → anon 키(브라우저)로는 접근 불가, service_role 키(백엔드)만 접근 가능
ALTER TABLE public.chat_sessions ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.chat_messages ENABLE ROW LEVEL SECURITY;
```

### 6-4. 메시지 하나가 저장되는 흐름

1. 사용자가 채팅 입력 → `Chat.jsx`가 `authFetch`로 `/chat` 호출 (토큰 첨부)
2. 백엔드가 토큰으로 `user_id` 확인
3. `session_id`가 없으면 새 대화방 생성(제목 = 첫 메시지 앞 22자), 있으면 **본인 소유인지 확인**
4. 해당 대화방의 최근 메시지 20개를 DB에서 불러와 GPT에 함께 전달
5. 질문·답변 2건을 `chat_messages`에 저장 후 응답 반환
6. GPT 호출이 첫 메시지부터 실패하면, 빈 대화방이 남지 않게 삭제

### 6-5. 프론트 변경

**chatApi.js** — `fetchChatSessions`, `sendChatMessage`, `deleteChatSession` (모두 `authFetch`를 인자로 받음)

**Chat.jsx** — 디자인은 그대로, 데이터 계층만 교체
- 화면 진입(및 계정 변경) 시 서버에서 내 대화 목록 로드, 로딩 중 "대화 기록을 불러오는 중…" 표시
- "새 대화"는 첫 메시지를 보낼 때 서버에 생성됨. 빈 새 대화가 여러 개 쌓이지 않게 재사용
- 대화방 삭제 시 DB에서도 삭제
- 전송 실패 시 방금 보낸 말풍선을 되돌리고 입력창에 글 복원
- 에러 문구를 "로컬 uvicorn 확인" 대신 "서버가 깨어나는 중일 수 있음"으로 변경

결과적으로 로컬 스토리지에는 로그인 유지용 `maeum:auth-user`만 남는다.

| 증상 | 원인 | 해결 |
|---|---|---|

| 특정 Vercel 주소에서만 채팅 실패 (CORS, `OPTIONS 400`) | 배포별 주소가 허용 목록에 없음 | 4장 |
| `/docs` 재시도 시 400 | 이미 가입된 이메일 / 메일 발송 한도 | 응답의 `detail` 확인, Confirm email 끄기 |
| 로그인 시 `Email not confirmed` | 이메일 인증 미완료 | Confirm email 끄고 해당 계정 재가입 |
| 채팅 저장 시 에러 (외래키) | `auth.users`에는 있는데 `profiles`에 없는 계정 (트리거 생성 전 가입) | Users와 profiles 계정 수 비교 → 누락 계정 삭제 후 재가입 |
| 채팅 테이블 저장 실패 | `SUPABASE_SERVICE_ROLE_KEY` 미등록 (RLS에 막힘) | Render에 키 등록 |
| Render 시작 시 `ModuleNotFoundError` | `DB` 폴더 위치/대소문자, requirements 누락 | 2-1 참고 |
| 1시간 후 채팅 끊김 | access_token 만료 | refresh_token 자동 갱신 (3-4) |
